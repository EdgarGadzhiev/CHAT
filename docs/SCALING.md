# NUR_CHAT — производительность и масштабирование

> Цифры ниже — **измеренные стоимости запросов в базе** на синтетических данных (150 000 сообщений, 3 000 пользователей,
> 20 000 сообщений с реакциями), а не полноценный нагрузочный тест с тысячами живых клиентов. Расчёты «на N человек» —
> оценки из этих измерений. Перед большим запуском сделайте пробную нагрузку (см. раздел 6).

## 1. Главная проблема, которую нашли и убрали — «эффект стада»
Раньше каждое новое сообщение рассылало всем онлайн-клиентам сигнал «перезапроси ленту», и **каждый** клиент скачивал
60 сообщений (≈24 КБ, ≈7 мс работы БД). При 200 людях онлайн и одном сообщении в секунду это ≈1,4 секунды работы БД
**на каждую секунду** — сервер стоял бы колом уже на небольшой аудитории.

Теперь:
1. **Сообщение приходит клиентам целиком по realtime** (приватный канал `city`, доступ только участникам с согласием) —
   никто ничего не перезапрашивает. Ответ на сообщение/реакцию/закрепление/удаление — тоже push (триггер в БД).
2. **Страховочная синхронизация** `feed_sync`: клиент присылает `{id: версия}` своих сообщений, сервер возвращает только
   изменившееся. В покое это **113 байт и ≈0,8 мс**. Интервал — 30 с (с разбросом ±25%, чтобы клиенты не били сервер синхронно).
3. **Если realtime недоступен** (упёрлись в лимит подключений тарифа) — клиенты автоматически переходят на опрос раз в ~8 с.
   Чат продолжает работать, просто с задержкой.
4. Пауза опроса в фоне, экспоненциальная пауза при ошибках, мгновенная досинхронизация при возврате в приложение.
5. **Реакции** считаются в самом сообщении (`messages.reactions`) — лента больше не делает подзапросы по таблице реакций;
   реакция пользователя отображается мгновенно (оптимистично), сервер возвращает итог.

## 2. Замеры (на одном соединении, мс на вызов)
| Операция | Было | Стало |
|---|---|---|
| Лента (60 сообщений) | 6,9 | **2,3** |
| Синхронизация в покое (`feed_sync`) | — (полная лента 24 КБ) | **0,8** (113 байт) |
| Отправка сообщения | 1,15 | 2,5 (теперь включает рассылку по realtime — зато нет N перезапросов) |
| Реакция | ≈1,5* | **0,76** |
| Список участников | 2,6 | **0,56** |
| Поиск участника | 5,3 | **2,5** (trigram-индекс) |
| `get_me` (профиль + счётчики) | 0,74 | 0,74 (теперь включает счётчики уведомлений и ЛС — на 2 запроса меньше) |

\* оценка по прежней схеме с подсчётом по таблице реакций.

**Оценка нагрузки на БД при 1 000 человек онлайн** (по измеренной стоимости вызовов): синхронизация ≈33 запроса/с × 0,8 мс,
профиль ≈17 запросов/с × 0,74 мс, 5 сообщений/с × 2,5 мс, реакции ≈10/с × 0,8 мс ≈ **0,06 ядра**. Узкое место смещается
с базы на **realtime-рассылку и трафик** (см. ниже).

## 3. Лимиты, которые код изменить не может (тариф Supabase)
Ваш проект сейчас на **Free**: 60 соединений с БД, ограниченный CPU/RAM, небольшой лимит realtime (≈200 одновременных
подключений и ≈100 сообщений/с рассылки), база 500 МБ, файлы 1 ГБ, трафик 5 ГБ/мес, проект «засыпает» после недели без активности.
(Проверьте актуальные цифры на странице тарифов Supabase — они меняются.)

Что это значит на практике:
- **до ~150–200 человек онлайн** Free-тариф справляется;
- **выше** — realtime-подключения кончаются, клиенты уходят на опрос (чат работает, но медленнее), а трафик/файлы упираются в квоту;
- для серьёзной аудитории нужен **Pro** (и при росте — больший размер сервера БД). Это самая действенная «оптимизация»:
  Supabase → Settings → Billing / Compute.

Трафик — главный «счёт» чата: одно сообщение ≈0,4 КБ × число людей онлайн. 1 000 человек × 5 сообщений/с ≈ 2 МБ/с ≈ 7 ГБ/час.
Поэтому для больших аудиторий включайте **медленный режим** и лимиты («Модерация → Настройки → Чат»).

## 4. Что ещё сделано для нагрузки
**База данных**
- `rate_limits` переведена в `UNLOGGED` (нет записи в журнал WAL), очистка каждые 15 минут, агрессивный autovacuum.
- Индексы: поиск участников (trigram), частичный индекс «топ/закреплённые», внешние ключи, непрочитанные уведомления.
- Одна выборка настроек вместо пяти на отправку сообщения; `get_me` отдаёт счётчики (меньше запросов с клиента).
- Личные сообщения: отметка «прочитано» пишется только если есть что отмечать; опрос 20 с (6 с, если канал не подключён).
- Защита хранилища: не более 60 файлов/час на пользователя; ежедневный поиск «осиротевших» файлов → очередь на удаление.
- Политики RLS без дублей (быстрее на каждом запросе), права функций закрыты для анонимов (проверяется после каждой миграции).
- Срок хранения сообщений (`chat_retention_days`, `dm_retention_days`, по умолчанию 0 = бессрочно) — чтобы база не разрасталась.

**Вход (Edge-функция `tg-auth`)**: при повторном входе 1 чтение + одна ссылка, **без записей**; лимиты регистрации мягкие по IP
(30/час — за одним IP мобильного оператора сидят тысячи людей) и общий потолок 600/час. Сессия хранится в браузере, заново входить
нужно редко.

**Клиент**
- Фото: в ленте грузятся **миниатюры ≈15–30 КБ** вместо файла 200–400 КБ (в 10–20 раз меньше трафика); полный файл — по нажатию.
- Код разбит: приложение ≈29 КБ (gzip) + библиотеки в отдельных файлах, которые кэшируются на год и не перезагружаются при обновлениях;
  панель модерации грузится только модераторам.
- Шрифт Manrope раздаётся с вашего сайта (быстрее, без запросов к Google и без передачи IP пользователей третьим лицам).
- Кэш-заголовки `immutable` для файлов сборки, `preconnect` к Supabase.
- Карточки сообщений перерисовываются только при изменении, чат остаётся в памяти при переключении вкладок (не перезапрашивается).
- Тихое повторное подключение при истёкшей сессии, баннер «нет соединения», страница-заглушка вместо белого экрана при ошибке.
- Защитные заголовки сайта (CSP, `nosniff`, Referrer/Permissions-Policy) — `public/_headers`.

## 5. Что смотреть и что делать
«Модерация → Система» показывает: участники, сообщения за час, размер базы, размер файлов, **соединения с БД** (полоса краснеет выше 75%).

| Симптом | Действие |
|---|---|
| Соединения с БД > 75% | повысить размер сервера БД (Supabase → Compute), временно включить медленный режим |
| База/файлы приближаются к лимиту | повысить тариф; включить срок хранения (`chat_retention_days`); «Система → Удалить файлы из очереди» |
| Чат «тормозит», точка у «Правил» жёлтая | realtime недоступен (лимит) — повысить тариф; чат работает через опрос |
| Наплыв спама | «Настройки → Чат»: медленный режим, отключить ссылки, `chat_enabled=false` на время |
| Нужно срочно отключить личные сообщения | «Настройки → Чат → Личные сообщения включены» |

## 6. Как проверить нагрузку перед запуском
1. Создайте 20–50 тестовых аккаунтов (или попросите друзей), включите «Модерация → Система» и наблюдайте «соединения» и «сообщений за час».
2. Проверьте поведение при отказе realtime: точка у «Правил» становится жёлтой, сообщения всё равно приходят (через ~8 с).
3. Для синтетической нагрузки используйте k6/Locust против `https://<проект>.supabase.co/rest/v1/rpc/feed_sync` с JWT тестовых пользователей.

## 7. Если аудитория вырастет ещё (тысячи одновременно)
- Рассылку сообщений вынести на **Cloudflare Durable Objects** (WebSocket-хаб): дешёвый fan-out без лимитов Supabase Realtime;
  сервер БД остаётся для записи и выборок. Схема и функции БД уже подходят (push-события с полным сообщением).
- Разделить общий чат на несколько комнат (районы/темы) — нагрузка и трафик делятся.
- Реплики чтения и кэш ленты на Cloudflare (лента общая для всех — хорошо кэшируется на 1–2 с).
- Перенос БД в РФ (см. `docs/LEGAL_SAFETY.md`) — тоже повод пересмотреть инфраструктуру; все миграции переносимы.
